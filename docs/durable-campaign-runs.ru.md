# Сохраняемые прогоны кампаний

Каждый запуск получает `crun_…` и отдельную запись прогресса. План сохраняет
имя кампании, порядок и ID сценариев, цель и timeout. Изменение или удаление
определения кампании не меняет этот план. Сами подписанные сценарии по-прежнему
берутся из доверенного каталога control-plane и проходят обычные проверки
подписи, RBAC, synthetic-only и ограничения времени.

## API и CLI

`POST /api/v1/asmodeus/campaigns/{id}/run` сохраняет запуск перед выполнением.
Без `background` ответ остаётся синхронным отчётом с дополнительными `id` и
`status`. С `{"background":true}` ответ `202` содержит сохранённый прогон.
Отключение HTTP-клиента не отменяет обработчик кампании.

- `GET /api/v1/asmodeus/campaign-runs`: история, новые первыми; фильтры
  `campaign_id`, `status`, `limit`.
- `GET /api/v1/asmodeus/campaign-runs/{id}`: план, результаты этапов,
  `superseded_results`, `resume_count`, `worker_active` и отчёт.
- `POST /api/v1/asmodeus/campaign-runs/{id}/cancel`: запрос отмены активного
  сценария и прекращение дальнейших этапов. `202 CANCELLATION_REQUESTED` ещё
  не подтверждает очистку; дождитесь итогового статуса и evidence сценария.
- `POST /api/v1/asmodeus/campaign-runs/{id}/resume`: явное фоновое возобновление
  `INTERRUPTED` или `CANCELLED`. Второй обработчик того же прогона, завершённый
  или неготовый к безопасному повтору прогон получает `409`.

```sh
asmodeus campaigns run --id CAMP-RANSOMWARE-CHAIN --background --timeout-sec 10
asmodeus campaigns runs --campaign-id CAMP-RANSOMWARE-CHAIN --limit 20
asmodeus campaigns status --id crun_…
asmodeus campaigns cancel --id crun_…
asmodeus campaigns resume --id crun_…
```

Для production CLI использует обычный `ASMODEUS_TOKEN`; `--role` и
`X-Apex-Role` работают только в явно разрешённом изолированном demo-режиме.
Чтение требует `ViewReports`; запуск, отмена и возобновление требуют прав на
каждую категорию сохранённого плана. Общая аварийная отмена останавливает также
допуск следующих этапов кампаний, доступных вызывающей роли.

## Сохранение и восстановление

При `ASMODEUS_STATE_DIR` прогресс записывается транзакционно в
`campaign_runs.json` версии 1, перед допуском сценария и после его результата.
ID сценарного прогона сохраняется до его допуска, чтобы восстановление могло
сопоставить этап с подписанным аудитом. Ошибка записи останавливает дальнейший
допуск; новая кампания при ошибке первой записи не запускает сценарии.

Для восстановления аудита настройте также `ASMODEUS_AUDIT_LOG` и постоянный
`ASMODEUS_AUDIT_SIGNING_KEY`. После рестарта незавершённые кампании становятся
`INTERRUPTED`; автоматического повтора нет. Если подписанный аудит уже содержит
завершённый этап, возобновление сохраняет его и начинает со следующего.
Незавершённая попытка переносится в `superseded_results`, а повтор получает
новый сценарный ID. Одновременные запросы могут допустить только один обработчик.

Реальный runner может продолжать работу после потери control-plane. Поэтому
при неподтверждённой очистке прошлого этапа возобновление блокируется. Отсутствие
аудита допущенного этапа также блокирует повтор. Симулятор не выполняет внешних
действий, поэтому его подписанный `INTERRUPTED` можно явно повторить. Отмена,
сохранённая до допуска сценария, безопасно возобновляется без сценарного аудита.

Сохраняются последние 200 `COMPLETED`/`FAILED`; активные и допускающие
возобновление прогоны не удаляются этой политикой. Снимок предполагает один
процесс-писатель в операторском каталоге, как каталоги кампаний и расписаний.
Без `ASMODEUS_STATE_DIR` состояние кампаний остаётся в памяти. При ошибке записи
прогресса исправьте хранилище и перезапустите control-plane для восстановления
`INTERRUPTED`; `worker_active:false` при незавершённом статусе не означает успех.

## Проверка

`cargo test --workspace --locked` покрывает гонки отмены/возобновления, обрыв
HTTP, отказ записи, сохранение и RBAC. `scripts/feature_smoke.py` проверяет
отмену, подтверждённую очистку и возобновление с настоящим локальным synthetic
runner. `scripts/campaign_smoke.py` принудительно завершает отдельный процесс
control-plane в режиме симуляции и проверяет рестарт, подписанный аудит,
сохранённый план, отсутствие повтора завершённых этапов и единственное
возобновление. Эти проверки входят в основной Jenkins pipeline; они не являются
приёмкой Linux BPF datapath, HA или внешнего production-развёртывания.
