## Эксплуатационный контракт аудита

При `ASMODEUS_AUDIT_LOG` обязателен `ASMODEUS_AUDIT_SIGNING_KEY`: путь к
64-байтовому Ed25519 secret key в hex-формате CLI `keygen`. Ключ должен переживать
рестарты и храниться отдельно от каталога сценариев. Без файлового журнала
допускается временный ключ для локальной симуляции. Ключ аудита используется
также для подписи lifecycle webhooks.

Журнал содержит все записанные ревизии. API `/runs` и экспорт возвращают
актуальную ревизию каждого run; порядок — первое появление run. Старый JSONL
с одной записью на run совместим по формату, но нужен исходный доверенный ключ.
Старые demo-журналы с утраченным временным ключом нельзя объявлять доверенными:
их следует сохранить отдельно и явно выбрать новый журнал/ключ. Автоматической
переподписи или удаления старых данных нет. Ротация ключей и проверка цепочки
всех исторических ревизий не реализованы; startup проверяет актуальные записи.

Хранилище рассчитано на **один процесс control-plane на один файл**. Mutex
сериализует клоны одного `AuditStore`, но не разные процессы. Это не HA-БД.
При аварийном завершении во время записи может остаться неполная последняя
строка: следующий запуск выдаст ошибку, а не отбросит историю. `sync_all`
применяется к файлу; гарантия сохранения новой directory entry при потере
питания отдельно не заявляется. Для большого журнала нужны retention,
индексы/пагинация и отдельное хранилище, поскольку актуальные записи находятся
в памяти и поиск по ID линейный.

Сохранение результата следует после инъекции. Ошибка аудита возвращает 500,
но не означает, что сценарий не выполнялся. Автоматически повторять такой
запрос нельзя: durable intent, idempotency key и reconciliation ещё нужны.
Таймаут gRPC также **не доказывает отмену или rollback** на удалённом runner.

## Незакрытые ограничения и следующий этап

| Приоритет | Подтверждённое ограничение | Что требуется |
| --- | --- | --- |
| P0 до эксплуатации на общем хосте | Runner проверяет подпись относительно ключа из самого `ExecuteRequest`; параметры исполнения передаются отдельно от подписанных байтов (`runner/service.rs`) | Закреплённый trusted key раннера и единый подписанный execution manifest; тесты подмены ключа/параметров |
| P0 до эксплуатации на общем хосте | Файловый scope — лексическая проверка; symlink не исключены. Canary cleanup удаляет весь target directory (`runner/canary.rs`) | Отдельная принадлежащая run песочница, операции через directory handles без следования symlink, удаление только принадлежащих run артефактов |
| P0 для обещаний safety | `/scenarios/abort` очищает локальную map завершённых runs, но не посылает отмену раннеру; DMS не получает `miss()`, CPU — константа, breaker проверяется после синхронной инъекции | RPC cancel + run ID, независимый таймер heartbeat, кооперативная отмена и подтверждённый cleanup; проверка потери control-plane на Linux-стенде |
| P1 | Runner делает файловый I/O в async handler; нет допуска только одного исполнения, cleanup-ошибки подавляются | Ограниченная очередь, blocking worker, отдельные песочницы, статус cleanup failure и тест конкурентных запусков |
| P1 | Успешные прогоны получают синтетические MTTD/MTTR и факт детекции даже при dispatch; тексты SOAR/cleanup не подтверждены внешней телеметрией | Явное происхождение измерений и pending feedback; реальные метрики не смешивать с simulated, отдельно фиксировать containment |
| P1 | Каталог сам подписывает загруженные файлы; часть DSL-параметров не управляет реальным исполнением; YAML — собственный ограниченный парсер | Доверенная поставка подписанных сценариев; единая типизированная схема DSL → execution; либо явное отклонение неподдерживаемых конструкций |
| P1 | JWT содержит tenant/permissions, но состояние глобальное, авторизация использует роль | До multi-tenant deployment определить и реализовать tenant isolation и enforcement permissions |
| P1 | Нет durable run intent/outbox; webhooks best-effort, campaigns/schedules/registry в памяти | Транзакционное хранилище, идемпотентность, восстановление незавершённых операций и доставки событий |
| P2 | Linux eBPF attach остаётся явной заглушкой; экспорт ClickHouse не является доставкой | Отдельная реализация и приёмочные проверки с Linux/CAP_BPF и реальной ClickHouse |

Эти ограничения не исправляются одним переносом функций между модулями.
Следующий связный этап — протокол исполнения и safety раннера; затем durable
оркестрация и достоверная отчётность.

## Проверки

- `cargo test --workspace --locked`: 165 тестов прошли, 0 failures/ignored; полный workspace, включая gRPC/mTLS и новые регрессии.
- `cargo clippy --workspace --all-targets --locked -- -D warnings`.
- `cargo fmt --all -- --check`.
- `python3 apex-contract/validate.py`.
- Регрессии: параллельные append/feedback, отмена запроса во время commit,
  ошибка диска, повреждённый JSONL, дублирующийся ID, рестарт с постоянным ключом,
  чужой ключ, Unicode hex, большие значения feedback, небезопасный DSL,
  недоступные раннеры, зависший event stream и terminal event без EOF.

Сетевые тесты требуют разрешения на локальный bind вне sandbox. Linux/eBPF
runtime, Semgrep и cargo-audit/cargo-deny в этой проверке не запускались.
