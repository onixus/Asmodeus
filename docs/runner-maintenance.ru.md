# Обслуживание раннеров

Оператор может временно исключить зарегистрированный раннер из маршрутизации,
сохранив его ID, endpoint и теги. Это доступно Admin, Red Team и DevSecOps;
Auditor, CISO и SecOps получают `403`, запрос без identity — `401`.
CLI использует обычный `ASMODEUS_TOKEN` (APEX JWT).

```sh
asmodeus runners drain --id probe-01
asmodeus runners list
# После завершения работ:
asmodeus runners resume --id probe-01
asmodeus runners ping --id probe-01
asmodeus runners list
```

API: `PATCH /api/v1/asmodeus/runners/{id}` с JSON `{"draining":true}`
для drain и `{"draining":false}` для resume. Ответ `200` содержит актуальный
`RunnerRecord`; неизвестный ID — `404`, отсутствующий/небулевый `draining`
или неизвестные поля — `422`. Повторные drain/resume идемпотентны.
Ошибка сохранения изменения возвращает `500`; неподтверждённое изменение
не публикуется в реестре. Это также относится к регистрации и удалению.

## Переходы и маршрутизация

- Drain переводит `active` или `unresponsive` в `draining`. Последующие выборы
  по ID, тегу и по умолчанию исключают этот узел. Heartbeat продолжает обновлять
  диагностические поля, но не снимает `draining`.
- Resume переводит `draining` в `unresponsive` и сбрасывает время heartbeat.
  Только healthy-ответ от новой проверки возвращает `active`; ошибка связи
  или `healthy=false` оставляют узел недоступным. Новую проверку выполняет
  watchdog либо оператор через `ping`. Resume уже активного узла ничего не меняет.
- Повторная регистрация того же ID может менять endpoint и теги, но сохраняет
  `draining` и ожидание heartbeat после resume. Изменение endpoint переводит
  активный узел в `unresponsive` до проверки нового адреса; диагностические
  поля старого endpoint сбрасываются. Обновление только метаданных сохраняет
  текущую проверенную информацию о здоровье. Старые heartbeat-ответы не меняют
  новую регистрацию.
- Результаты heartbeat принимаются только для последней начатой проверки
  текущей регистрации и состояния обслуживания. Отложенный ответ до drain,
  resume, перерегистрации или удаления/повторного создания ID отбрасывается.
  `GET /runners/{id}/ping` возвращает `registry_updated`: `false` означает,
  что ответ уже устарел; поле `healthy` описывает сам ответ удалённого раннера.
- Если активных узлов нет, запрос без target получает `502`; явный ID/тег,
  не имеющий активного соответствия, — `404`. Fallback к симуляции или статическому
  endpoint не выполняется после регистрации хотя бы одного узла, даже если
  затем удалён последний. В новой конфигурации без раннеров доступна симуляция.

## Границы

Drain действует с момента изменения реестра на **последующие выборы** раннера.
Сценарий, уже выбравший узел, может продолжить допуск/dispatch после ответа PATCH.
Drain не отменяет такие прогоны, не подтверждает cleanup и не доказывает отсутствие
работы на узле. Для остановки конкретного прогона используйте cancel и проверьте
его терминальное состояние и `cleanup_confirmed` перед выключением раннера.

При заданном `ASMODEUS_STATE_DIR` реестр и maintenance-состояние сохраняются
в `runners.json`. Без этого параметра они остаются в памяти и теряются после
рестарта. Это не распределённая блокировка: нужен **один writer-процесс на файл**,
каталог должен быть защищён от записи посторонними. Удаление ID и новая
регистрация создают новый узел; это административная операция.

## Сохранение и восстановление

- Версионированный JSON snapshot содержит ID, имя, endpoint, теги, время
  регистрации и `draining`. Наблюдения heartbeat (CPU, версия, время и здоровье)
  не сохраняются и не вызывают дисковых записей.
- При первом запуске с `ASMODEUS_STATE_DIR` snapshot создаётся до запуска HTTP,
  включая начальный `default-runner` из `ASMODEUS_RUNNER_ENDPOINT`, если он задан.
  И начальный, и восстановленный раннер ждут нового healthy heartbeat. Узел
  с сохранённым `draining=true` остаётся исключённым даже после healthy-ответа.
- Существующий snapshot является источником конфигурации. Изменение
  `ASMODEUS_RUNNER_ENDPOINT` не переопределяет адрес, не снимает drain и не
  воскрешает удалённый default-runner. Меняйте узлы через API/CLI. После удаления
  последнего узла зарегистрируйте нужный раннер заново; автоматического перехода
  к симуляции нет. Snapshot, созданный из пустой demo-конфигурации, сохраняет
  возможность симуляции, пока впервые не зарегистрирован раннер.
- Регистрация, drain/resume и удаление сериализованы. Запись во временный файл
  (`0600` на Unix), `sync_all` и атомарный rename завершаются до публикации
  конфигурации в памяти. Отмена HTTP-запроса не прерывает начатый commit;
  после потери ответа проверьте актуальный реестр. Чтение и heartbeat не держат
  блокировку во время дисковой записи; свежие health-данные не затираются.
- Повреждённый JSON, неизвестная версия, дубли ID, неверный endpoint или ошибка
  чтения останавливают startup. Автоматического сброса/перезаписи конфигурации нет.
  Сохраните повреждённый файл для разбора и восстановите проверенную резервную
  копию при остановленном control-plane. Отсутствие файла означает первичную
  инициализацию, поэтому не удаляйте snapshot для обычного рестарта.
- Подтверждается восстановление после рестарта процесса. Файл не является
  подписанным аудитом, HA-хранилищем или гарантией сохранения directory entry
  при отключении питания. Для переноса стенда сохраняйте `runners.json` вместе
  с остальными файлами state и ключами согласно контракту аудита.

## Проверка

Unit-тесты проверяют drain/resume, повторную регистрацию, ответы heartbeat
в обратном порядке и смену endpoint/ID. HTTP-тесты проверяют RBAC, валидацию,
блокировку маршрутизации и возврат после gRPC heartbeat. После сборки
`python3 scripts/feature_smoke.py` проверяет реальные CLI-команды и два процесса
на изолированных loopback-портах, сохранение drain/регистрации/удаления после
рестарта, отказ записи и startup с повреждённым snapshot, а затем остальные
сценарии приёмки. Unit-тесты также покрывают конкурирующие записи, отмену
HTTP-ожидания и сохранение heartbeat, пришедшего во время commit.
