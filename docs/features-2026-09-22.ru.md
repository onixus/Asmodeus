# Выполнение, feedback и постоянное состояние — 2026-09-22

Реализованы четыре направления: управляемый жизненный цикл прогона,
происхождение результатов Blue Team, восстановление кампаний/расписаний и
исполнение параметров DSL. Это контракт текущей реализации и инструкция
для одного control-plane с доверенными runner-процессами.

## Запуск и отмена

`POST /api/v1/asmodeus/scenarios/:id/run` принимает:

```json
{"background": true, "timeout_sec": 15, "target_override": "runner-id-or-tag"}
```

`background=true` возвращает HTTP 202 с `run_id` и `status_url` после записи
подписанного `QUEUED` в аудит. Без этого параметра запрос ждёт терминального
результата. Потеря HTTP-клиента не отменяет уже допущенное исполнение.
`timeout_sec` может только сократить `safety.max_duration_sec` манифеста.
`target_override` выбирает зарегистрированный раннер и не меняет файловый scope.

`GET /runs/:id` возвращает подписанный audit record и отдельный `live_state`.
Поле `live_state` — оперативный прогресс; оно не входит в подпись. Подписанный
статус остаётся `QUEUED` до фиксации терминального результата.

`POST /runs/:id/cancel` и `POST /scenarios/abort` запрашивают отмену только
тех категорий, которые разрешены роли оператора. HTTP 202/ответ abort не
подтверждает cleanup. Подтверждение находится в итоговом
`evidence.cleanup_confirmed`; `cleanup_status=SUCCESS` выставляется только
после терминального сообщения раннера. Завершённый прогон отменять повторно
не нужно; его результат остаётся в истории.

Runner допускает одно активное исполнение, выполняет файловый I/O в blocking
worker и создаёт эксклюзивный каталог `<signed target>/<run_id>` с правами 0700.
Удаляется только этот каталог. Существующие каталоги с тем же ID и symlink в
canary-пути отклоняются. Отмена проверяется между файловыми операциями и во
время ожидания. Heartbeat с текущим run ID продлевает lease; отсутствие его
в течение 3 секунд, разрыв execution stream и дедлайн останавливают инъекцию
и запускают cleanup. Обычный watchdog ping lease не продлевает.

Терминальные результаты: `COMPLETED`, `CANCELLED`, `TIMED_OUT`, `CONTROL_LOST`,
`FAILED`, `CLEANUP_FAILED`. Ошибка транспорта фиксируется как `FAILED` с
неподтверждённой очисткой. После рестарта control-plane незавершённые записи
переходят в `INTERRUPTED`, без автоматического повтора. Если терминальный
аудит не записался, оперативный статус — `AUDIT_PERSISTENCE_FAILED`; результат
потребует разбирательства, а не слепого повторного запуска.

CLI:

```sh
asmodeus run --scenario RANSOMWARE_CANARY_SPIKE --background --timeout-sec 15
asmodeus runs get --id RUN_ID
asmodeus runs cancel --id RUN_ID
```

Для штатной аутентификации CLI читает `ASMODEUS_TOKEN` с APEX JWT. `--role`
работает только при явно включённом локальном `ASMODEUS_ALLOW_ROLE_HEADER=1`.
Примеры API выше используют общий префикс `/api/v1/asmodeus`.

## Доказательства и метрики

Каждая новая подписанная запись содержит `evidence`:

- `execution_mode`: `runner`, `simulated` или `legacy_unverified`;
- `feedback_received`: поступила явная обратная связь;
- `contained`: оператор подтвердил сдерживание;
- `cleanup_confirmed`: раннер подтвердил собственную очистку;
- `failure_reason`: причина отказа/прерывания, если есть.

Раннер не объявляет детекцию или SOAR-сдерживание из факта исполнения.
До feedback используются `PENDING_FEEDBACK` и нулевые значения без образца
измерения. Симуляция в control-plane и network SimBackend явно маркируются
`simulated` и исключаются из оценок защиты, даже после ручного feedback.
Старые записи без `evidence` сохраняют проверяемость старой подписи, но не
становятся подтверждёнными измерениями автоматически.

`POST /runs/:id/feedback` принимает `detected`, `contained`, `mttd_ms`,
`mttr_ms`, `detection_source`, `containment_action`. Детекция требует MTTD;
сдерживание требует детекции и MTTR. Feedback возможен после завершения
исполнения, не меняет его статус и не подтверждает cleanup. Это данные,
заявленные аутентифицированным отправителем; независимая аттестация сенсора
и автоматический коннектор Ferrum/SOAR сюда не входят.

MTTD усредняется по подтверждённым детекциям, MTTR — по подтверждённым
сдерживаниям. API/отчёт содержат количества live feedback, pending и simulated;
Prometheus — `asmodeus_feedback_received`, `asmodeus_pending_feedback`,
`asmodeus_simulated_runs`, `asmodeus_detection_samples`,
`asmodeus_containment_samples`. Ноль без образцов не означает мгновенную защиту.
При отсутствии данных отчёт показывает `NO DATA`; Govern/Identify не получают
автоматические 100%. Карта NIST — результаты упражнений, не сертификат соответствия.

Экспорт ClickHouse сохраняет подписанные `evidence` в строке `evidence_json`.
Для существующей таблицы перед импортом нужен дополнительный столбец:

```sql
ALTER TABLE apex.asmodeus_runs
ADD COLUMN IF NOT EXISTS evidence_json String DEFAULT 'null';
```

## Кампании и расписания

`ASMODEUS_STATE_DIR` включает JSON snapshots `campaigns.json` и `schedules.json`.
Без этой переменной каталоги временные. Изменения сериализованы, пишутся во
временный файл с `sync_all` и публикуются через rename до ответа API. Ошибка
чтения/десериализации останавливает startup; повреждённый каталог не заменяется
seed-данными. Удаления и паузы переживают перезапуск.

Расписания сохраняют время допуска, run ID, итог, baseline, ограниченную историю
(50 запусков) и алерты (200). Время попытки записывается до dispatch; ошибка
раннера не вызывает повтор каждую итерацию polling. После рестарта незавершённое
задание получает `INTERRUPTED` и соблюдает свой интервал. Seed-расписания по
умолчанию выключены. Повторный ID при создании отклоняется. Пауза запрещает
следующий допуск; текущий прогон останавливается через cancel/abort.

Роль создателя сохраняется без повышения привилегий. Категория проверяется
при создании, включении и выполнении. Каждая попытка имеет запись истории;
только live feedback меняет MTTD/drift. Повтор одинакового feedback не добавляет
второй sample/alert и не сдвигает расписание. Поздний feedback сохраняется у
своего run; он не переписывает baseline последнего запуска.

Шаги кампании сортируются по положительному уникальному `order`; проверяются
сценарии и права на все категории. Цепочка останавливается при неуспешном шаге,
сохраняя частичный ответ и ID допущенного прогона. Дефиниции кампаний постоянные;
исполнения кампании остаются синхронной цепочкой отдельных audit runs.
Background/resume целой кампании не реализованы и явно отклоняются.

## Исполняемый DSL и ключи

Control-plane и runner компилируют один подписанный манифест в `ExecutionPlan`.
Действие выбирается по `spec.action.type`, поэтому собственный scenario ID
работает без добавления ветки в runner. Параметры за пределами allowlist,
неверные типы, неизвестные поля и отключение lease отклоняются.

| Действие | Параметры |
| --- | --- |
| `synthetic_canary_encrypt` | `file_count` (1–200), `chunk_size_kb` (1–256), `io_rate_per_sec` (1–1000) |
| `c2_beacon` | `file_count` (1–100) |
| `exfiltration_canary` | `chunk_size_kb` (1–256) |
| `latency_spike` | `latency_ms` (0–5000), `jitter_ms` (0–1000), `loss_percent` (0–50), `iface` |
| `k8s_escape_probe`, `credential_canary`, `log_tamper_canary`, `persistence_canary`, `watchdog_probe` | Только общий `duration_ms` |

`duration_ms` (0–120000) доступен всем действиям и ограничен signed deadline
(1–300 с). IO rate означает число canary-файлов в секунду. CPU budget (1–85%)
кооперативно ограничивает время рабочего потока по thread CPU clock на Unix;
это не host-wide cgroup quota. Canary-путь берётся из подписанного target scope,
общий объём ограничен 20 MiB. CIDR применим только к network action. Selector
пока не исполняется и отклоняется. `target_scope.type` — описательная метка;
`expected_outcome` — ожидание, не наблюдавшийся результат.

JSON поддерживается полностью в пределах схемы; YAML — ограниченные вложенные
key/value mapping и scalar, без anchors, sequences и сложных конструкций.
Для сложного авторинга используйте JSON. Ошибка в файле из
`ASMODEUS_SCENARIOS_DIR` теперь останавливает startup.

Для настоящего runner задайте:

- control-plane: `ASMODEUS_SCENARIO_SIGNING_KEY=/secrets/scenario.key`;
- runner: `ASMODEUS_RUNNER_TRUSTED_KEY=/secrets/scenario.pub`;
- постоянный аудит: `ASMODEUS_AUDIT_LOG=/data/audit.jsonl`,
  `ASMODEUS_AUDIT_SIGNING_KEY=/secrets/audit.key`;
- каталоги: `ASMODEUS_STATE_DIR=/data/state`.

Ключи создаются `asmodeus keygen --name /secrets/scenario` и отдельно для audit.
Runner закрепляет trusted public key, проверяет подпись и соответствие
дублирующихся RPC-параметров подписанному плану. TLS-настройки остаются
`ASMODEUS_RUNNER_TLS_*` / `ASMODEUS_CLIENT_TLS_*`; локальный plaintext не
становится production-настройкой из-за наличия подписи.

## Приёмка и границы

`cargo test --workspace --locked`: 178 тестов прошли, 0 failed/ignored.
`cargo clippy --workspace --all-targets --locked -- -D warnings`,
`cargo fmt --all -- --check` и `python3 apex-contract/validate.py` прошли. `cargo build --workspace --locked && python3 scripts/feature_smoke.py`
проверяет два настоящих процесса: подписанный custom DSL, async cancel,
очистку только своих файлов, feedback, restart audit/catalogs, scheduler/drift,
тайм-аут и маркировку network simulation. Стенд использует временные ключи,
loopback и отдельный canary-каталог; после проверки процессы и данные удаляются.

Состояние рассчитано на один control-plane; HA, idempotency keys, durable
webhook outbox и постоянный registry ещё не реализованы. File snapshots и audit
не являются общей транзакционной БД; при ошибке обновления schedule после
сохранения feedback API сообщает об обеих стадиях. Для сбоя питания не заявлена
гарантия сохранения новой directory entry. Sandbox использует проверки путей,
а не descriptor-relative операции: нужен каталог, защищённый от записи чужими
процессами. SIGKILL самого раннера не выполняет Rust cleanup. Полная namespace/
cgroup-изоляция и восстановление runner после crash — отдельные задачи.

Linux eBPF attach остаётся явной заглушкой. Реальные задержки/потери сети и
production-интеграции датчиков этим этапом не заявляются.
